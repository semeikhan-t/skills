# Hackathon TZ Skill

Скилл для генерации профессионального технического задания для хакатона.
Итоговый документ — полноценный `.md` файл, который читает вся команда и AI-агенты.

---

## Шаг 1 — Сбор информации (ОБЯЗАТЕЛЬНО перед генерацией)

Перед тем как писать ТЗ, задай пользователю все вопросы ниже **в одном сообщении**.
Не генерируй ТЗ до получения ответов. Если какой-то ответ уже есть в контексте — не спрашивай повторно.

### Блок A — Задача хакатона
```
1. Название хакатона и его тема/направление?
2. Описание задачи / проблемы от организаторов (можно вставить текст целиком)?
3. Ограничения от организаторов (стек, платформа, формат сдачи)?
4. Есть ли готовое API от организаторов? Если да — вставь документацию или описание.
5. Длительность хакатона (например: 24 часа, 48 часов, 3 дня)?
```

### Блок B — Команда
```
6. Состав команды: имя + роль каждого участника
   Пример: Азамат — бэкенд, Дана — фронтенд, Марат — ML, Айгерим — дизайн/PM
```

### Блок C — Стек
```
7. Есть ли предпочтения по стеку технологий?
   Если нет — агент предложит оптимальный для хакатона вариант.
```

---

## Шаг 2 — Предложение стека (если не задан)

Если пользователь не указал стек, предложи оптимальный вариант для хакатона:

**Рекомендуемый стек по умолчанию:**
| Слой | Технология | Причина |
|------|-----------|---------|
| Frontend | React + Vite + TailwindCSS | Быстрый старт, большая экосистема |
| Backend | Django + Django REST Framework | Батареи включены: ORM, admin, auth из коробки |
| База данных | PostgreSQL | Надёжность, нативная поддержка Django ORM |
| Авторизация | JWT | Простота реализации |
| Деплой | Docker Compose | Единое окружение для команды |
| CI/CD | GitHub Actions (если нужен) | Автодеплой на финал |

Адаптируй стек под задачу: если ML — добавь PyTorch/scikit-learn; если мобильное — React Native или Flutter; если блокчейн — уточни сеть.

Спроси подтверждение: **"Подходит такой стек? Или хочешь что-то изменить?"**
Продолжай только после подтверждения.

---

## Шаг 3 — Генерация ТЗ

После получения всех ответов сгенерируй `.md` файл по структуре ниже.
Сохрани файл как `ТЗ_[название_хакатона].md`.

---

## Структура итогового документа

### 1. Шапка документа

```markdown
# ТЗ: [Название проекта]
> Хакатон: [Название хакатона]
> Длительность: [N часов / дней]
> Дата генерации: [дата]
> Версия: 1.0

---
```

### 2. Описание проекта

```markdown
## 📋 Описание проекта

### Проблема
[Чёткое описание проблемы, которую решает проект]

### Решение
[Что именно мы делаем и как это решает проблему]

### Целевая аудитория
[Кто пользователь, кто выигрывает от решения]

### Ключевая ценность
[1–3 пункта — в чём главная польза]
```

### 3. Состав команды

```markdown
## 👥 Команда

| Имя | Роль | Зона ответственности |
|-----|------|----------------------|
| [Имя] | [Роль] | [Кратко: что делает] |
```

### 4. Стек технологий

```markdown
## 🛠 Стек технологий

| Слой | Технология | Назначение |
|------|-----------|-----------|
| Frontend | ... | ... |
| Backend | ... | ... |
| БД | ... | ... |
| ... | ... | ... |

### Структура репозитория

Всегда монорепо. Структура по умолчанию:

\`\`\`
project/
├── frontend/          # React + Vite
│   ├── src/
│   └── package.json
├── backend/           # Django + DRF
│   ├── apps/
│   ├── config/
│   ├── manage.py
│   └── requirements.txt
├── docker-compose.yml
├── .env.example
└── README.md
\`\`\`

Если есть ML-компонент — добавить `ml/` на том же уровне.
Если есть мобильное приложение — добавить `mobile/` на том же уровне.
```

### 5. Функциональные требования (MVP)

```markdown
## ✅ Функциональные требования

### Must Have (MVP — без этого не сдаём)
- [ ] [Фича 1] — [краткое описание]
- [ ] [Фича 2] — [краткое описание]

### Should Have (если останется время)
- [ ] [Фича]

### Won't Have (явно в скоп не входит)
- [Что намеренно исключаем]
```

### 6. API Endpoints

```markdown
## 🔌 API Endpoints

### [Модуль / домен, например: Auth]

#### POST /api/auth/register
**Описание:** [что делает]

**Request:**
\`\`\`json
{
  "field": "type // описание"
}
\`\`\`

**Response 200:**
\`\`\`json
{
  "field": "type // описание"
}
\`\`\`

**Errors:**
| Код | Причина |
|-----|---------|
| 400 | [описание] |
| 422 | [описание] |

---
[Повтори блок для каждого endpoint]
```

> **Правило генерации endpoints:** Выведи все endpoint'ы на основе функциональных требований.
> Группируй по доменам (Auth, Users, Tasks, и т.д.).
> Если организаторы дали своё API — опиши интеграцию отдельным разделом.

### 7. Разбивка задач по разработчикам

```markdown
## 👤 Задачи по разработчикам

> Принцип: минимальные зависимости между разработчиками.
> Каждый работает в своей зоне и блокирует других только через чёткие интерфейсы (API контракт, типы, моки).

### [Имя] — [Роль]
- [ ] **[Задача 1]** — [описание, ожидаемый результат]
- [ ] **[Задача 2]** — [описание, ожидаемый результат]

**Зависит от:** [имя] — [что именно нужно получить и когда]
**Предоставляет:** [имя] — [что отдаёт и когда]
```

> **Правило разбивки:**
> - Бэкенд-разработчик(и) — API + БД + бизнес-логика
> - Фронтенд-разработчик(и) — UI + интеграция с API (работают по mock'ам пока бэк не готов)
> - ML/DS — модели и инференс, экспонируют через отдельный микросервис
> - Дизайн/PM — макеты, компонентная система, координация
> - Нет пересечений по файлам и модулям там, где это возможно

### 8. Roadmap и зависимости

```markdown
## 🗺 Roadmap

### Индивидуальные roadmap'ы

#### [Имя] — [Роль]
| Этап | Задача | Дедлайн (ч. от старта) |
|------|--------|------------------------|
| 1 | [задача] | +[N]ч |
| 2 | [задача] | +[N]ч |

[Повтори для каждого члена команды]

---

### Граф зависимостей задач

\`\`\`mermaid
graph TD
    A["[Имя]: Задача 1"] --> B["[Имя2]: Задача 2"]
    A --> C["[Имя3]: Задача 3"]
    B --> D["[Имя2]: Задача 4"]
    C --> D
    style A fill:#4CAF50,color:#fff
    style D fill:#2196F3,color:#fff
\`\`\`

> 🟢 Зелёный — стартует первым  
> 🔵 Синий — зависит от других  
> Стрелка A → B означает: B не может начаться без A
```

> **Правило Mermaid:** Используй `graph TD` (сверху вниз). Группируй задачи одного разработчика визуально.
> Имена нод должны быть уникальными. Используй цвета для различия разработчиков.

### 9. Функциональные блоки и чеклисты проверки

```markdown
## 🔍 Этапы и проверка

> После завершения каждого функционального блока — разработчик проводит быструю ручную проверку по чеклисту.
> Если проверка не пройдена — см. Fallback инструкции.

---

### Блок 1: [Название блока, например: Авторизация]
**Ответственный:** [Имя]
**Готово когда:** [краткий критерий]

#### ✅ Чеклист проверки
- [ ] **[Пункт]** — [что именно проверить: например, POST /auth/login возвращает JWT токен]
- [ ] **[Пункт]** — [описание]
- [ ] **[Пункт]** — [описание]

#### 🔁 Fallback (если что-то не работает)
> Если блок не прошёл проверку:
- **Если [конкретная проблема]** — упрости до [конкретное упрощение]
- **Если нет времени** — вырежи [что именно] и замени на [заглушку/хардкод]
- **Минимально рабочая версия блока:** [описание — что должно работать хотя бы]

---
[Повтори блок для каждого функционального блока]
```

### 10. Риски и ограничения

```markdown
## ⚠️ Риски и ограничения

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| [Риск 1] | Высокая/Средняя/Низкая | Критичное/Среднее/Низкое | [Что делать] |

### Узкие места
- **[Узкое место]:** [описание проблемы и как обойти]
```

> **Правило генерации рисков:** Агент сам выявляет узкие места на основе стека, команды и функционала.
> Типичные риски на хакатоне: интеграция внешнего API организаторов, ML-модель не успевает обучиться,
> бэк и фронт не состыковались по контракту, нехватка участников в последние часы.

### 11. Готовность к демо

```markdown
## 🎯 Готовность к демо

> Финальная проверка перед презентацией. Пройти за 15–20 минут до конца хакатона.

### Техническая готовность
- [ ] **Приложение запускается** — `docker-compose up` или эквивалент работает без ошибок
- [ ] **Основной сценарий работает** — [ключевой user flow от начала до конца]
- [ ] **Нет критических ошибок в консоли** — проверить DevTools / логи сервера
- [ ] **Данные не пустые** — есть тестовые данные / seed для демо
- [ ] **API отвечает** — базовые endpoint'ы возвращают корректные ответы

### Демо-сценарий
- [ ] **Сценарий прописан** — у кого-то есть чёткий план "что показываем и в каком порядке"
- [ ] **Демо-данные подготовлены** — тестовые аккаунты, контент, примеры
- [ ] **Слайды / питч готовы** — если требуются организаторами

### Сдача
- [ ] **Репозиторий** — код запушен, README заполнен
- [ ] **Деплой** — [ссылка на live-версию если требуется]
- [ ] **Документация** — данное ТЗ актуально и отражает итоговый продукт

#### 🔁 Fallback перед демо
> Если что-то не работает за 20 минут до конца:
- Приоритет 1: основной пользовательский сценарий работает хотя бы на хардкоде
- Приоритет 2: UI показывает правильные данные (даже если они статичные)
- Приоритет 3: остальное — не критично, можно объяснить словами на презентации
```

## Шаг 4 — Финальный вывод

После генерации документа:
1. Сохрани файл как `ТЗ_[название].md`
2. Предложи его пользователю через `present_files`
3. Напиши в чат: **"ТЗ готово. Хочешь что-то скорректировать — состав команды, стек, scope?"**

---

## Правила агента

- **Язык документа:** всегда русский, независимо от языка входных данных
- **Mermaid:** всегда использовать для графа зависимостей, синтаксис проверять
- **JSON в API:** все request/response — строго в json-блоках с комментариями
- **Чеклисты:** GitHub-style `- [ ]` с описанием каждого пункта
- **Fallback:** обязателен для каждого функционального блока и для финального демо-чеклиста
- **Зависимости:** задачи разработчиков должны быть максимально независимы; пересечения — только через чёткий интерфейс
- **Стек:** если не задан — предложить и дождаться подтверждения перед генерацией
- **Не генерировать ТЗ** до получения ответов на все вопросы из Шага 1
